# M1: Queue, events, stop and worker deadlines

## Objective and prior state

Finish 5D before implementing 5E. The existing asynchronous API and persistent
event IDs work in basic cases, but admission/deduplication race, replay can miss
live events, and the streaming test blocks. Execution currently uses an
uninterruptible thread with no enforced tool deadline.

## Build and verification plan

1. Serialize queue admission and stop; persist initial task, request mapping and
   queued event before making work visible. Recover abandoned queued tasks.
2. Read ordered events from SQLite for both replay and live streaming; send a
   snapshot after initial replay. Validate reconnect cursors and test an actual
   authenticated streaming connection with bounded network timeouts.
3. Extract a latched cancellation barrier and mutation lock. Use one scheduling
   thread and at most one owned spawned process for execution, with cooperative
   cancellation followed by bounded termination for nonresponsive workers.
4. Preserve uncertain effects as unknown, record the action ledger, and never
   automatically replay a stopped/timed-out action. Retain instance ownership
   until the scheduler and its child have exited.
5. Test concurrent admission, capacity, event ordering/reconnect, stop races,
   deadline expiry, child crash, cooperative stop and mutation exclusion.

## Checks

Run the explicit foundation, storage, queue/events and supervisor test files.
Run Ruff on changed Python files. Tests use temporary workspaces and local test
servers, without opening apps, recording audio or contacting model services.

## Final behavior and interfaces

- `POST /api/tasks` returns HTTP 202 and a task ID. At most one task executes
  and three await execution. Queue overflow returns HTTP 429 without admission.
- `X-Client-Request-ID` (also `X-Request-ID` or `client_request_id`) is durable.
  The first accepted request owns the ID; later uses return its existing task
  without replacing arguments or executing again, including after restart.
- Task record, request mapping and initial event are committed in one SQLite
  transaction before the scheduler can see the task.
- Events use persistent integer IDs. SSE accepts `Last-Event-ID`, `cursor`, or
  `after`; explicit query cursor takes precedence. Replay is paged in batches
  of 100 through a fixed initial boundary, followed by task snapshots and live
  polling at 50 ms. Every live read uses the same database ordering source.
- Snapshots reuse the last replay ID and do not allocate lifecycle event IDs.
  Task-scoped streams send one snapshot; the general stream snapshots saved
  tasks. Invalid cursors return 422, a cursor ahead of the log returns 409, and
  an unknown task stream returns 404. Heartbeats are emitted every 15 seconds.
- `safety/cancellation.py` owns the latched emergency barrier.
  `runtime/locks.py` owns the shared mutation slot; queued and synchronous calls
  use the same scheduling path.
- `runtime/supervisor.py` spawns at most one owned action worker. A tool's finite,
  positive `timeout_seconds` includes startup, execution and verification.
  Stop and deadline expiry signal its cancellation Event. After 250 ms grace,
  the supervisor terminates the child, waits up to 500 ms, and escalates to kill
  with another 500 ms wait if necessary. It reaps the worker before another task
  can mutate anything. There are no automatic action retries.
- `ToolSpec.execute_cancellable`, when supplied, receives the cancellation
  Event. Execute/verify functions must be importable top-level callables for
  Windows spawn. Unpicklable callables are rejected before process creation.
- `POST /api/stop` closes the barrier, signals the active worker and cancels
  pending work. Its acknowledgement does not promise an already-applied change
  was undone. Poll the task result/events for the final state. Stop stays
  latched until service restart.
- A task stopped before dispatch is cancelled. A dispatched task with uncertain
  effects after Stop, crash or timeout is unknown, with a machine-readable error
  code and action ledger reference. The note or partial effect may still exist.
- Task results include an optional `action_id`. Restart cancels abandoned queued
  work and classifies interrupted execution/ledger entries without replay.
- Service close waits for the scheduler and owned worker before releasing the
  instance lock. Incomplete shutdown raises and retains directory ownership.

## Optional emergency shortcut

After restarting the service with the following setting, Ctrl+Alt+Pause invokes
the same stop path. Registration is owned and cleaned up on its dedicated
Windows thread. No administrator privileges or keyboard-hook package is needed.

```powershell
$env:VICTUS_EMERGENCY_HOTKEY = '1'
uv run victus serve
```

`GET /api/health` reports `emergency_hotkey` as `disabled`, `registered`,
`unavailable_or_in_use`, or `error`. A conflicting shortcut or missing Pause key
does not remove the authenticated API Stop control. The shortcut is disabled
by default and still needs an intentional physical-key check on this laptop.

## Remaining boundaries

Adapter subprocesses must not launch untracked child workers. Actual UIA,
audio and browser session ownership and cancellation remain separately
qualified when those adapters are implemented. Spawned workers are real process
isolation for interruption, not an OS security sandbox. Full effect
reconciliation/approval recovery remains M4; the present behavior records
uncertainty instead of guessing or replaying. No cancellation latency percentile
or broad desktop reliability claim is inferred from these fixture tests.
