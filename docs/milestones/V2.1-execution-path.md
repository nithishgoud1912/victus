# V2.1 - One bounded execution path

Created before production edits, 2026-10-17.

## Objective and prior state

Preserve the workspace-only, exclusive-create note tool while resolving strict
generic requests through the registry. Deterministic workflows and planners
already use `Dispatcher.dispatch_step`; the task worker uses a second synchronous
`dispatch` implementation. The queue records dispatch intent before worker-side
validation; proposals are not strict and typed admission does not revalidate
in-process input. Workflow scope checks exist but do not serialize against the
process resource slot. Bootstrap advertises unqualified browser/desktop stubs.

Baseline: implementation commit `64a0a22127a2d450a8d8bb4047cf76cae0cc4995`,
616 backend tests, 20 frontend tests, native/MCP packaged note checks passed.
See `V2-progress.md` for the exact baseline fingerprint and limits. The existing
package remains a baseline artifact and will not represent modified V2.1 code.

## Implemented files and interfaces

`tools/contracts.py`: strict identity-free ToolRequest/ActionProposal input;
retain ActionRequest as the narrow note contract. `tools/registry.py`: resolve
and validate each registered schema, keeping trusted metadata local.
`tools/dispatcher.py`: synchronous compatibility wrapper delegates to the
existing async step sequence, including target revalidation, resources, Stop,
intent, adapter and exact-True independent verification.
`tools/steps.py`: trusted worker identity/context/resource ownership.
`safety/policy.py`: deterministic scope/risk checks. `tasks/service.py`,
`tasks/queue.py`, `runtime/supervisor.py`: registry-driven admission and owned
worker/ledger lifecycle without accepting user IDs, approval flags or verifiers.
`bootstrap.py`, `tools/desktop.py`: stop advertising unqualified desktop stubs;
retain qualified workflow-local registrations. `workflows/qualification.py`:
adapt owner-loop entry only if necessary to share dispatch_step.
`api/app.py`: strict generic transport and safe rejected-input response.
`tests/test_foundation.py`, `tests/test_supervisor.py`,
`tests/test_notepad_workflow.py`, `tests/worker_support.py`: generic API and
admission contracts, unchanged note behavior, reviewed workflow risk context and
import-light spawned effect fixtures. `tools/filesystem.py` and the native note
adapter/verifier were inspected and retained without edits.

The generated dashboard OpenAPI/types change only to match ToolRequest. No
general-purpose command UI or unqualified desktop entry is exposed.

Inputs: untrusted tool name/argument data only (plus opaque target references for
planner proposals); trusted task/action identity, scopes, permits and verifiers
come from service code. Outputs: bounded verified data or failed/blocked/unknown
outcomes; an unproved possible effect is never successful. No Notepad-specific
dispatcher or new desktop qualification claim is introduced.

## Implementation and source contracts

Implementation remains a dirty source change on base commit
`64a0a22127a2d450a8d8bb4047cf76cae0cc4995`. Final source SHA-256:
`16a4aac7f5b6fd88fb7bc4f628d3d3d63172671979a90f5ab16de49f8e38aa3a`.
The exact file manifest is `.local/v21-final-source.json`; private environment
files and runtime payloads are excluded.

The public [ToolRequest](../../backend/victus/tools/contracts.py) has only
`tool` and `arguments`. The note-specific ActionRequest still binds
`Literal["fs.create_note"]` to NoteArguments. Planner proposals add opaque target
and observation references, not authority. Service-assigned WorkerAuthority
carries task ID, action ID, scopes and a trusted risk ceiling over the owned
process channel. It is not an API request type.

Both compatibility and planner/workflow callers reach
[Dispatcher.dispatch_step](../../backend/victus/tools/dispatcher.py):

```python
outcome = asyncio.run(self.dispatch_step(action, context))
```

The final effect commitment is in that shared sequence, after current policy,
permit, Stop and deadline checks:

```python
context.ledger.mark_dispatching(action_id)
dispatched = True
```

Adapter completion alone is insufficient. The registered verifier must return
exactly True, and possible but unproved effects stay unknown. The parent task
service additionally requires a verified ledger entry before accepting success.

Startup recovery now occurs only during service startup. Worker/context creation
ensures schema availability without retiring its live owning task. The original
public queue/started/terminal event sequence is preserved; internal workflow steps
retain their own safe audit events. The
[cross-module decision](../decisions/002-shared-execution-path.md) records resource
ownership, risk policy, async/native owner boundaries and qualification limits.
