# V2.2 - Durable task state, queue and events

## Objective and prior state - 2026-10-18

Verify one active task plus three pending tasks, atomic durable admission,
request-ID deduplication, ordered authenticated replay/live delivery, passive
snapshots and conservative recovery. This record was created before V2.2
production edits. Preserve the existing schema unless an actual gap requires an
additive migration.

Base revision: `64a0a22127a2d450a8d8bb4047cf76cae0cc4995`, with the existing
uncommitted V2.1 implementation preserved. V2.1 qualified 648 backend tests and
20 frontend tests, plus real source note/UI checks. Runtime roots for this stage
are isolated under `.local/`; personal runtime data and credentials are excluded.

## Inspection and changes

Already present: the queue admission lock, bounded pending queue, one supervised
worker, a transaction for task/initial event/request mapping, persisted mapping,
SQLite AUTOINCREMENT event IDs, one database ordering source for replay and live
reads, snapshot-only reads and crash recovery without action replay. Action
effects already have prepared/dispatching/applied/verified/unknown states and
restricted payload storage separate from audit metadata.

Identified gaps: later task state updates and their events used separate commits;
a crash between them can leave an incomplete event history. The migration runner
claims atomic migration files but uses executescript followed by a separately
committed schema version, allowing partial schema changes on failure. Verify
both with fault injection and fix their transaction boundaries without new tables.

Exact production and test files changed: `backend/victus/storage/database.py`,
`backend/victus/storage/migrations.py`, `backend/victus/tasks/events.py`,
`backend/victus/tasks/queue.py`, `backend/tests/test_storage.py`,
`backend/tests/test_queue_events.py`. Documentation changes: this record,
`V2-progress.md`, `docs/supported-workflows.md`,
`docs/decisions/003-task-event-transactions.md`, and
`docs/release/v2.2-task-state-evidence.json`.

No SQL migration file, table definition, action-ledger/payload schema, API
contract, task-service contract or frontend component was changed for V2.2.
Those existing implementations were inspected and qualified through their public
paths. The generated API remains the V2.1 transport contract.

Inputs: strict ToolRequest plus optional client request ID; authenticated event
cursor/task ID. Outputs: original or new task ID, current TaskResult, sequenced
safe events, passive snapshots, or explicit capacity/cursor errors. Caller text
must stay out of task/event/action metadata. Queued work is cancelled on restart;
potentially dispatched effects become unknown and are never automatically retried.
