# M4 / 8D — Reconciliation, retry, resume and compensation

## Effect reconciliation

`backend/victus/recovery/reconcile.py` inspects prepared, dispatching, applied and
unknown action records using explicitly registered, version-matched read-only
verifiers. It loads retained arguments and checks their ledger hash before any
probe. Unsupported versions, missing/expired/changed payloads, inconclusive
responses, verifier errors and deadlines produce an unknown verdict.

Each verifier returns `EffectProof("present" | "absent" | "unknown", evidence)`.
Conclusive verdicts require evidence. The receipt verifier used by the M4 fixture
checks the operation ID, recipient and content hash independently of the failed
submission response. A lookup must establish authoritative absence, not merely
fail to find a page element or encounter a network error.

Reconciliation requires the trusted owner to stop and join the owned worker
first (`quiesced=True`). Probes must be asynchronous and read only, with a bounded
deadline. Synchronous native probes cannot be registered directly; an integration
using blocking native APIs must put that probe behind the existing supervisor.
An asyncio timeout alone does not prove a blocked native operation has stopped.

Reconciliation evidence is stored as a separate retained output payload, referenced
by a migration-0006 `recovery_reconciliations` row and a safe audit event. Evidence
payloads are bounded to 128,000 bytes and retained for 24 hours. Raw errors and
argument bodies are not copied into the audit event.

An uncertain dispatched action remains **unknown** in its original ledger record,
even when recovery later proves its receipt exists. The separate reconciliation
verdict reports that proof without rewriting the interrupted execution history or
claiming that the entire task completed. Unstarted prepared attempts are cancelled.

## Bounded retry permission

`backend/victus/recovery/retry.py` reserves one recovery attempt by default, capped
at two per original action. SQLite transactions serialize reservations, preserve
counts across restart and debit shared action/recovery allowances. Reopened
callers cannot replenish shared counters by supplying an older budget snapshot.
Planning/model requests and schema repairs still use the existing shared planner
budget when a caller needs a new decision.

Only tools explicitly classified SAFE or IDEMPOTENT qualify. Tools also declare
`external_write`; its default is true, so unknown adapters fail closed. Automatic
external writes are denied even when a tool claims idempotency. A manually
requested write retry additionally needs a fresh, version/argument-matched absent
verdict (within 60 seconds), then fresh normal policy, observation and approval.
Present, uncertain, stale or unsupported effects do not permit a write retry.

A retry reservation grants no dispatch authority and does not execute a tool.
Its returned remaining budget already includes the reserved action/recovery debit;
the owner must persist/use that budget and must not charge the same reservation
again. Normal graph attempts remain independently bounded by the graph's shared
budget. This milestone does not enable automatic retries for unqualified adapters.

## Resume and graph integration

`backend/victus/recovery/resume.py` invalidates old pending/approved records and
retires their permits during crash recovery. It cancels unstarted prepared work
and marks interrupted dispatch/applied work unknown. Its asynchronous `resume()`
can run supported reconciliation probes, but never dispatches a write.

Service startup now uses this recovery path. This deliberately supersedes 8C's
earlier startup behavior that retained live approval requests: after a service
restart, previous authority is invalid and a fresh observation/review is required.
Normal approval resolution and review resume within the running service continue
to use the durable review interrupt without invalidating a newly reviewed request.

`AgentServices.reconciler` is an optional trusted composition dependency. When
configured, the graph inspects receipts after an uncertain outcome or interrupted
execute node, then stops without proposing another submission. No verifier is
guessed or loaded from model output. An unconfigured adapter remains unknown.
Reconciliation time is included in the graph's active-work budget.

## Explicit compensation

`backend/victus/recovery/compensation.py` offers only registered forward/reverse
tool-version pairs. It requires independent present evidence and retained bound
arguments before a trusted builder can construct a reverse proposal. There is no
generic undo generated by a model.

Dispatch requires a separate prepared reverse action and its own fresh permit,
then goes through the normal dispatcher: argument schema, required scopes,
policy, live target/observation, cancellation, ledger and postcondition checks.
The original approval cannot authorize compensation. An unsupported reverse
operation is not offered; no production destructive reverse tool was invented
for this milestone. Tests register an explicit fixture reversal and prove both
policy denial and successful verified execution.

## M4 submission acceptance tests

`tests/submission_support.py` runs a loopback-only HTTP submission service backed
by SQLite. It records every POST separately from its durable receipt ID, so a
duplicate request cannot hide behind an idempotent receipt table.

`tests/test_m4_submission.py` exercises the real graph, authenticated approval API,
dispatcher, permit store and receipt verifier for:

1. Denial: no POST and no receipt.
2. Expiry: resolution conflicts and nothing is submitted.
3. Permit reuse: one POST/receipt; reuse and repeated resume cannot submit again.
4. Changed recipient: the original approval cannot authorize the changed target.
5. Changed content: modified proposal arguments invalidate the bound approval.
6. Stop while the approval is still pending: confirmation is rejected and nothing
   is submitted.
7. Timeout after receipt commit: the server saves a receipt before delaying its
   response beyond the worker's deadline. Recovery independently retrieves the
   receipt, retains unknown execution status, rejects automatic retry, and performs
   no second POST across repeated resume/recovery.

`tests/test_recovery.py` additionally covers unsupported/missing/stale proof,
verifier errors/deadlines, retry classification and budget exhaustion, concurrent
reservations, approval invalidation and supported compensation through policy.
No external submissions, real-model benchmark, physical voice test or native
desktop qualification are part of these M4 fixtures.
